## 2. What was actually wrong

Six fixes across four commits (padding, line heights, `clip={false}`, scaled
line boxes, manual font scaling, frozen metrics) were shipped to the phone and
all failed. That was itself the signal: no style could reach the bug because no
style was causing it.

Two experiments settled it:

1. **Metro was made to serve a release-equivalent bundle** (`--no-dev --minify`,
   Hermes bytecode). It rendered whole words — so minification, `__DEV__` and
   bytecode were all innocent, leaving the _asset_ path.
2. **The working and broken screenshots were cropped and compared.** They were
   in **different typefaces**:

   | Build                 | Painted | Typeface                                         |
   | --------------------- | ------- | ------------------------------------------------ |
   | dev client over Metro | `Play`  | thin, double-story `a` — the **system fallback** |
   | release APK           | `Pla`   | chunky, single-story `a` — **Fredoka**           |

The dev build had never been rendering your fonts at all; it only looked correct
because measurement and painting agreed on the fallback face.

**The mechanism:** `useFonts` registers a font family _after_ JavaScript starts.
In a release APK the first labels are measured against the narrow fallback face,
then painted with the wider real face into a box that is never re-measured. The
overflow is the missing letters. That explains every detail of the symptom:

- worse with larger font size — the width error is a percentage of the font
  size, and at 1.0x the label's own padding absorbed it
- worse with longer words — `Home` → `Hom`, `Puzzles` → `Puzzl`,
  `Daily Puzzle` → `Daily`
- release only — a dev build never loaded the font that overflows

## 3. The fix

The `expo-font` **config plugin** now embeds all five families in `app.json`, so
the build copies them into `android/app/src/main/assets/fonts/` and Android
resolves each family **synchronously, before the first measure** — there is no
window in which the wrong face can be measured.

Confirmed inside the shipped APK:

```
assets/fonts/Fredoka_600SemiBold.ttf
assets/fonts/Fredoka_700Bold.ttf
assets/fonts/Nunito_400Regular.ttf
assets/fonts/Nunito_700Bold.ttf
assets/fonts/Nunito_800ExtraBold.ttf     (ci-10 had none of these)
```

This was an app-wide latent bug — every `Text` in the app, not only the three
labels that happened to be reported.

Supporting changes: `src/shared/fonts.test.ts` (new guard test — fails if a
family is ever left to runtime-only loading), the tab bar's height now scales
with its label, and the comments that recorded dead theories were corrected.

### Theories tested and ruled out

- **Descenders / glyph shapes** — `Home` → `Hom` has no descender.
- **`overflow: hidden` on `PopSurface`** — clip disabled, no change.
- **Horizontal padding budget** — 3pt then 8pt of ink room, no change.
- **The gradient layer on the Play face** — moved to an overlay, no change.
- **Prop identity / re-measure on update** — frozen module constants, no change.
- **Display density** — reset to the physical density, no change.
- **React Native's font-scale path** — bypassed entirely with manual scaling, no
  change. RN 0.86.2's changelog has no relevant fix either, so the upgrade that
  was considered would not have helped.
- **JS mode** — a `dev=false`, minified, Hermes-bytecode bundle rendered whole
  words, so minification and `__DEV__` were never involved.

### Evidence that pointed the wrong way for hours

Maestro's accessibility dump reported the **full** strings inside **full-size**
boxes (`Play` laid out 187px wide) while the pixels stopped cleanly after `Pla`.
That reads as "layout is fine, painting truncates", which sent the search into
the paint pipeline. It was true but incomplete: the box was full-size _for the
fallback face_, and painting was correct _for Fredoka_. The comparison that
resolves the contradiction is the typeface crop in §2 — worth doing first next
time a text bug appears only in release.

## 9. The debugging loop, and the gotchas hit while building it

Reusable recipe:

```bash
gh release download ci-N --pattern "*.apk"
adb uninstall com.puzzled.app && adb install puzzled-ci-N.apk
adb shell settings put system font_scale 1.3
adb shell am force-stop com.puzzled.app && adb shell am start -n com.puzzled.app/.MainActivity
adb shell screencap -p //sdcard/s.png && adb pull //sdcard/s.png shot.png
```

Environment traps worth remembering, all hit today:

- **Git Bash rewrites `/sdcard/...`** into a Windows path, so `screencap` fails
  with a usage message. Use `//sdcard/...`, and keep local paths in `E:/...`
  form.
- **PowerShell `>` corrupts binaries** — never redirect `screencap` output; use
  `screencap` to a file then `adb pull`.
- **Two adb versions** — `C:\adb` is still first in the _system_ PATH and its
  server (v31) fights the new client (v41). Prefix the PATH per command, or
  remove the old entry from an admin shell.
- **`adb reverse` is lost whenever the adb server restarts**, and the dev client
  then says "There was a problem loading this project". Re-add it after any
  `kill-server`.
- **An interrupted `adb install` wedges the server** — a 171MB transfer that is
  cancelled leaves adb hanging on every later command. `taskkill /F /IM adb.exe`,
  then run big installs as a background job.
- **Metro dies with the shell that launched it.** Start it detached and poll
  `curl http://127.0.0.1:8081/status` for `200` before pointing the phone at it.
- **CI cancels in-flight runs on a new push** (`cancel-in-progress: true`), so do
  not push while waiting on a build you intend to test.
- **Docs-only pushes skip the build** (`paths-ignore`), which is why this file
  costs no CI minutes.

## 10. Loose ends (none blocking)

- **iOS**: the plugin embeds the files there too, but iOS takes the family name
  from inside the font file, so it will still use the runtime path and still has
  the latent race. Untested — there is no iOS build. Noted in the design doc.
- **Old `C:\adb`** is still in your _system_ PATH and wins in new terminals;
  removing it needs an admin shell.
- **Optional cleanup**: now that the real cause is fixed, the manual font
  scaling could be replaced by React Native's own `allowFontScaling`. It is kept
  because it makes the tab bar's height and its label size derive from one
  constant; the trade-off is that a font-size change mid-session applies at the
  next launch.
- **Expo is one patch behind** (`57.0.8` installed, `57.0.15` available). Not
  related to anything here; `npx expo install --check` when convenient.
