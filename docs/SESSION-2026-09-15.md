### 2.1 Post-merge regression caught by tests

The first full run after merging failed exactly 2 treasure-screen tests:
"shows the day, stop count and difficulty tier" expected `Day 1 — stop 1 of 7 ·
Easy` but rendered `Start the trail` (streak 0), and the reward test found the
right title but `recordOnce` never fired.

**Root cause:** the test helper built day keys with `date.toISOString().slice
(0,10)` (UTC), while the app's `dateKey`/`streakFrom` (`src/data/daily.ts`) use
**local** midnight. The suite was green exactly while UTC and local agreed on
"today"; once local midnight crossed (and after the merge's timing), a
`dayKey(-1)` completion bucketed two local days back, so `streakFrom` walked
over an empty day and the payment effect never re-ran. Fix (`741f94e`): the
test `dayKey()` now uses the app's own `dateKey(new Date() + offset days)` —
local, deterministic on every device/timezone, and `12:00Z` completedAt stamps
bucket to the same local day in every `±12h` timezone. No product code changed.

### 5.1 adb input-tap quirk (documented, not a product bug)

Injected `adb shell input tap` reached mid-screen controls (chips, whole
treasure card) but **not** the top-left back arrow nor the bottom Start Puzzle
button on Select Difficulty — those taps only produced the ambient audio loop,
with the screen verified pixel-identical across 4 timed frames after the tap
(touch never reached RN; window is full-screen edge-to-edge, 1240×2772, no
inset). Real finger taps worked on every control. Likely a per-device
touch-injection/gesture-band sensitivity quirk of this OPPO build's injected
touches near the display edges, **not** app code — recorded so future adb
driving picks targets mid-screen.

### 5.2 Bug deferred by the user: corner snap

Reported during play: after mis-dropping a piece at/near a corner, the correct
corner piece **no longer snaps** when placed aligned — no "clunk", stays loose.
Investigation state (user is handling later; not fixed):

- Snap is center-distance only (`dropPiece`, `session.ts:139`) vs the piece's
  OWN solved slot, so a wrong piece never "locks" at a foreign corner — this is
  about a **loose** miss left covering the slot.
- Loose pieces render **after** locked clusters (`puzzle-board.tsx` ~1787/1798),
  so a loose miss always draws over anything that then locks beneath it, and
  hit-testing (`looseBoxes` topmost-first, ~1443) makes each new grab at that
  corner pick up the covering loose piece instead — reads as "the correct piece
  won't fit again."
- `clampPieceToBoard` (`tray-geometry.ts:234`) pins overhanging drops at the
  corner (position → (0,0)), which parks misses exactly on the corner slot.
- Candidate fix (untried): after a successful snap, evict loose pieces that
  overlap the newly locked slot back to the tray (position.y = boardHeight,
  same mechanism as a tray-drop), clearing the covering piece so the corner
  piece shows and stays grabbable.
