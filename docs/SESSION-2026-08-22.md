## 2. What was actually wrong

Six fixes across four commits (padding, line heights, `clip={false}`, scaled
line boxes, manual font scaling, frozen metrics) were shipped to the phone and
all failed. That was itself the signal: no style could reach the bug because no
style was causing it.

Two experiments settled it:

1. **Metro was made to serve a release-equivalent bundle** (`--no-dev --minify`,
   Hermes bytecode). It rendered whole words — so minification, `__DEV__` and
   bytecode were all innocent, leaving the _asset_ path.
2. **The working and broken screenshots were cropped and compared.** They were
   in **different typefaces**:

   | Build                 | Painted | Typeface                                         |
   | --------------------- | ------- | ------------------------------------------------ |
   | dev client over Metro | `Play`  | thin, double-story `a` — the **system fallback** |
   | release APK           | `Pla`   | chunky, single-story `a` — **Fredoka**           |

The dev build had never been rendering your fonts at all; it only looked correct
because measurement and painting agreed on the fallback face.

**The mechanism:** `useFonts` registers a font family _after_ JavaScript starts.
In a release APK the first labels are measured against the narrow fallback face,
then painted with the wider real face into a box that is never re-measured. The
overflow is the missing letters. That explains every detail of the symptom:

- worse with larger font size — the width error is a percentage of the font
  size, and at 1.0x the label's own padding absorbed it
- worse with longer words — `Home` → `Hom`, `Puzzles` → `Puzzl`,
  `Daily Puzzle` → `Daily`
- release only — a dev build never loaded the font that overflows

Every earlier theory (descenders, `overflow: hidden`, the gradient layer, prop
identity, React Native's font-scale path) is dead.

---

## 3. The fix

The `expo-font` **config plugin** now embeds all five families in `app.json`, so
the build copies them into `android/app/src/main/assets/fonts/` and Android
resolves each family **synchronously, before the first measure** — there is no
window in which the wrong face can be measured.

Confirmed inside the shipped APK:

```
assets/fonts/Fredoka_600SemiBold.ttf
assets/fonts/Fredoka_700Bold.ttf
assets/fonts/Nunito_400Regular.ttf
assets/fonts/Nunito_700Bold.ttf
assets/fonts/Nunito_800ExtraBold.ttf     (ci-10 had none of these)
```

This was an app-wide latent bug — every `Text` in the app, not only the three
labels that happened to be reported.

Supporting changes: `src/shared/fonts.test.ts` (new guard test — fails if a
family is ever left to runtime-only loading), the tab bar's height now scales
with its label, and the comments that recorded dead theories were corrected.

## 7. Loose ends (none blocking)

- **iOS**: the plugin embeds the files there too, but iOS takes the family name
  from inside the font file, so it will still use the runtime path and still has
  the latent race. Untested — there is no iOS build. Noted in the design doc.
- **Old `C:\adb`** is still in your _system_ PATH and wins in new terminals;
  removing it needs an admin shell.
- **Optional cleanup**: now that the real cause is fixed, the manual font
  scaling could be replaced by React Native's own `allowFontScaling`. It is kept
  because it makes the tab bar's height and its label size derive from one
  constant; the trade-off is that a font-size change mid-session applies at the
  next launch.
